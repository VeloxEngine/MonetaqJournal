Structuring Relational Databases in Supabase

By Engineering Team • October 2026 • 9 min read • PostgreSQL Architecture

At its core, Supabase is not an arbitrary abstraction or a proprietary document store—it is raw, unadulterated PostgreSQL. This distinction is paramount. When developers migrate from NoSQL document databases like MongoDB or Firebase Firestore to Supabase, they frequently make the mistake of dumping large, unstructured JSON blobs into columns rather than leveraging relational integrity, foreign key constraints, and declarative schema design.

1. Relational Modeling: Moving Beyond Document Blobs

A well-architected relational model enforces data consistency at the engine level rather than relying on brittle client-side application code. Before writing queries, you must design your tables around the principles of Third Normal Form (3NF):

  • First Normal Form (1NF): Each column contains atomic (indivisible) values, and each record is identified by a unique primary key.
  • Second Normal Form (2NF): All non-key attributes are fully dependent on the primary key, eliminating partial key dependencies.
  • Third Normal Form (3NF): All attributes are dependent only on the primary key, removing transitive dependencies.

2. Choosing the Right Primary Key: UUIDs vs. Identity Integers

In Supabase, identity can be structured using either auto-incrementing integers (BIGINT GENERATED ALWAYS AS IDENTITY) or universally unique identifiers (UUID).

  • UUIDv4 / UUIDv7: Ideal for public-facing resource IDs, user tables, and distributed systems where IDs must be generated client-side without colliding. Supabase's auth.users uses UUID primary keys.
  • BIGINT Identity: Excellent for internal ledger tables, time-series events, and high-frequency append-only write streams due to lower B-Tree index fragmentation and compact 8-byte footprint.

3. Production DDL Schema Blueprint

Consider an enterprise SaaS application featuring users, organizations, projects, and many-to-many team memberships. Here is the production DDL script demonstrating proper foreign keys, constraints, and cascading actions:

migrations/001_initial_schema.sql 
-- 1. Enable pgcrypto for UUID generation
CREATE EXTENSION IF NOT EXISTS "pgcrypto";

-- 2. Organizations Table
CREATE TABLE public.organizations (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name TEXT NOT NULL CHECK (char_length(name) >= 2),
    slug TEXT NOT NULL UNIQUE CHECK (slug ~* '^[a-z0-9-]+$'),
    created_at TIMESTAMPTZ NOT NULL DEFAULT timezone('utc'::text, now()),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT timezone('utc'::text, now())
);

-- 3. Profiles Table (Linked to auth.users)
CREATE TABLE public.profiles (
    id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
    email TEXT NOT NULL UNIQUE,
    full_name TEXT,
    avatar_url TEXT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT timezone('utc'::text, now())
);

-- 4. Organization Memberships (Junction Table for Many-to-Many)
CREATE TABLE public.organization_members (
    organization_id UUID NOT NULL REFERENCES public.organizations(id) ON DELETE CASCADE,
    user_id UUID NOT NULL REFERENCES public.profiles(id) ON DELETE CASCADE,
    role TEXT NOT NULL CHECK (role IN ('owner', 'admin', 'member', 'viewer')),
    joined_at TIMESTAMPTZ NOT NULL DEFAULT timezone('utc'::text, now()),
    PRIMARY KEY (organization_id, user_id)
);

-- 5. Projects Table (One-to-Many with Organizations)
CREATE TABLE public.projects (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    organization_id UUID NOT NULL REFERENCES public.organizations(id) ON DELETE CASCADE,
    name TEXT NOT NULL,
    metadata JSONB DEFAULT '{}'::jsonb,
    is_archived BOOLEAN NOT NULL DEFAULT false,
    created_at TIMESTAMPTZ NOT NULL DEFAULT timezone('utc'::text, now())
);

4. High-Performance Indexing Strategies

Writing a clean schema is only half the battle; without proper indexing, table scans will degrade your database performance as rows accumulate:

  • B-Tree Indexes: PostgreSQL automatically indexes primary keys and unique constraints. Always manually add B-Tree indexes on your foreign keys (e.g., projects(organization_id)) to accelerate JOIN operations.
  • Composite Indexes: When queries routinely filter by multiple columns (e.g., finding active projects for an org), construct composite indexes matching the filter order: CREATE INDEX idx_projects_org_status ON public.projects(organization_id, is_archived);
  • GIN Indexes for JSONB: If you must store semi-structured JSON attributes, apply a Generalized Inverted Index (GIN) to allow sub-millisecond key lookups: CREATE INDEX idx_projects_metadata ON public.projects USING gin (metadata);
Database Insight: Foreign Keys Are Not Automatically Indexed

Unlike primary keys, PostgreSQL does not automatically create indexes on foreign key columns. If you frequently join projects onto organizations, omitting an index on organization_id will cause PostgreSQL to perform a sequential scan across the entire table.

5. Automated Auditing with PostgreSQL Triggers

To maintain accurate updated_at timestamps without polluting frontend payloads, declare a reusable SQL function and bind it to a trigger:

migrations/002_triggers.sql 
CREATE OR REPLACE FUNCTION update_updated_at_column()
RETURNS TRIGGER AS $$
BEGIN
    NEW.updated_at = timezone('utc'::text, now());
    RETURN NEW;
END;
$$ language 'plpgsql';

CREATE TRIGGER trigger_update_organizations_timestamp
    BEFORE UPDATE ON public.organizations
    FOR EACH ROW
    EXECUTE FUNCTION update_updated_at_column();

6. Summary Checklist for Supabase Relational Design

When reviewing your schema before production launch:

  1. Are all relationships defined with explicit FOREIGN KEY and ON DELETE policies?
  2. Are all foreign keys backed by B-Tree indexes?
  3. Is Row Level Security (RLS) enabled on every public table?
  4. Are check constraints (regex, string lengths, enum bounds) enforcing data sanitation at the engine layer?
